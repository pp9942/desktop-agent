写提交信息之前，按下面的流程做，不要直接动手：

1. 先用 bash 跑 `git diff --stat` 和 `git status --short`，确认这次到底改了哪些文件——
   提交信息描述的是实际发生的变更，不是任务描述的复述。
2. 对每个改动较大的文件，用 read 看一眼改动前后的上下文，弄清「为什么改」。
   提交信息的第一行说 what，正文说 why——评审的人最想知道的是 why。
3. 按这个格式产出，然后交给用户确认，不要自己执行 git commit：

   ```
   <类型>: <不超过 50 字的what>

   <why：动机、背景、影响面，1-3 行>
   ```

   类型只允许这几种：feat / fix / docs / refactor / test / chore。

反例（不要这样写）：
- "更新代码" —— 什么都没说；
- "修复了 bug" —— 没说是什么 bug、怎么修的；
- 把五件不相干的事写进一条提交 —— 应该建议拆成多次提交，每次一件事。

正例：
```
fix(tools): edit 在原文出现多次时拒绝执行并返回命中行号

模糊匹配会改错地方（曾把 mean 的修改打到 median 上），
改错的代价比多问一句大，所以不唯一时直接拒绝。
```

如果用户要提交的信息涉及多个类型，主动建议按类型拆分提交，
并给出每一拆的建议顺序（先依赖后使用）。

范围纪律：提交信息只描述将要提交的内容。如果 git status 里有不相关的脏文件，
先列出来问用户要不要一起提交，不要默默全塞进去；
`.env`、密钥、`config.json` 这类文件无论用户怎么说都不能进提交，这是硬规则。

历史一致性：写之前用 `git log --oneline -8` 看最近几条的措辞习惯，
沿用这个仓库已经形成的类型词和语言（本仓库用中文正文），不要突然换成英文风格。
